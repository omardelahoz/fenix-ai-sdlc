# SPEC-202: Workspace Layout (Workspace ABI)

## 1. Executive Summary
The `_fenix` directory is the physical interface between the User, their Git repository, and the Fénix Operating System. It is the **Workspace ABI**.
Fénix categorizes all data generated during the SDLC into four strict tiers: **Persistent**, **Recoverable**, **Temporary**, and **Operational**. This categorization dictates exactly what must be committed to source control and what must be ignored, ensuring total project reproducibility without polluting the Git history.

## 2. Directory Structure
When a user runs `fenix init` inside a software project, the following structure is generated:

```text
my-project/
├── src/
├── docs/
├── README.md
│
└── _fenix/
    ├── workspace.json   # Fénix Package Definition
    │
    ├── artifacts/       # Persistent knowledge
    ├── config/          # Persistent Project configuration & overrides
    ├── workflows/       # Persistent Workflow states
    │
    ├── knowledge/       # Expensive Recoverable Knowledge (Embeddings, Indexes, Graphs)
    ├── cache/           # Fast Recoverable Cache (Inference caching)
    │
    ├── temp/            # Temporary scratchpads
    │
    ├── journal/         # Operational WAL (Kernel & Runtime)
    └── snapshots/       # Operational state checkpoints
```

## 3. The `workspace.json` Manifest
The `workspace.json` is the equivalent of `package.json` for Fénix. It defines the constraints and metadata for the project:

```json
{
  "workspace_version": "1.0",
  "artifact_schema": "1.0",
  "runtime_abi": "1.2",
  "plugin_api": "2.0",
  "project": {
    "name": "ecommerce-api",
    "created": "2026-07-13",
    "default_workflow": "workflows/main.wdl"
  }
}
```

## 4. Data Categorization & Git Strategy
The physical ABI relies on a deterministic `_fenix/.gitignore` file generated by Fénix.

### A. Persistent Data (✅ Committed to Git)
Data that defines the *Knowledge* and *Configuration* of the project. If lost, the LLMs would have to regenerate the entire project from scratch.
- **`workspace.json`**: The core Fénix manifest.
- **`artifacts/`**: Contains the JSON serialized forms of `RequirementsIR`, `ArchitectureIR`, `TestIR`, etc.
- **`config/`**: Contains environment configurations, plugin overrides, and project settings.
- **`workflows/`**: Contains the serialized orchestration intent (e.g., the WDL files and PMFs specific to this project).

### B. Expensive Recoverable Data (✅ Committed to Git or Stored Remotely)
Data that is derived from artifacts but costs too much time/compute to regenerate from scratch.
- **`knowledge/`**: Contains vector embeddings, semantic graphs, and knowledge indexes. Not temporary cache. Should be preserved across machines.

### C. Fast Recoverable Data (❌ Ignored in Git)
Data that speeds up execution but can be deterministically regenerated quickly.
- **`cache/`**: Contains Inference Hashes and AST parse results.

### D. Temporary Data (❌ Ignored in Git)
- **`temp/`**: Short-lived files used by plugins (e.g., downloading a massive PDF to extract text before deleting it). Safe to wipe via `fenix clean`.

### E. Operational Data (❌ Ignored in Git)
Data required to survive a reboot of the Fénix daemon, but irrelevant to another developer pulling the repository.
- **`journal/`**: The Write-Ahead Logs (WAL) for the Kernel Memory and the Runtime FSM.
- **`snapshots/`**: Checkpoints of the Orchestration Tree (`WorkflowInstance` -> `PipelineInstance`).

## 5. The Auto-Generated `.gitignore`
Fénix enforces the Workspace ABI by injecting and maintaining a `.gitignore` inside the `_fenix` directory:

```gitignore
# _fenix/.gitignore
# AUTO-GENERATED BY FÉNIX. DO NOT MODIFY.

# Ignore Recoverable & Temporary Data
cache/
temp/

# Ignore Operational Data
journal/
snapshots/

# Allow Persistent & Expensive Data
# (workspace.json, artifacts, config, workflows, knowledge are explicitly tracked)
```

## 6. Conclusion
By treating the Workspace as a formal ABI with strict data categorization, Fénix guarantees that a multi-agent AI project remains completely deterministic. A developer can `git clone` a Fénix project, run `fenix resume`, and the system will organically rebuild the cache and operational data using the persistent artifacts and knowledge graphs as its source of truth.
