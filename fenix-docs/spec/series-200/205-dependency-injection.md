# SPEC-205: Dependency Injection & Service Composition

## 1. Executive Summary
Fénix prohibits the use of global state (Singletons) or magic Dependency Injection (DI) frameworks (like Spring, Wire, or FX) in its core engine.
Fénix relies entirely on **Explicit Constructor Injection** and manual **App Wiring** in the `main.go` entrypoint. This guarantees absolute traceability of the service graph, eliminates hidden side-effects, and makes unit testing trivial.

## 2. The Anti-Singleton Philosophy
Global variables (e.g., `var GlobalKernel *Kernel`) make testing in parallel impossible and hide dependencies. 
In Fénix:
- No package is allowed to define global state.
- If a component needs the `Scheduler`, it must request it in its constructor.
- `init()` functions are strictly forbidden unless absolutely necessary for low-level Go runtime hooks.

## 3. Constructor Injection
Every service, engine, and client in the Fénix architecture must provide a `New*` constructor that accepts its dependencies as explicit interfaces defined in `pkg/contracts`.

```go
// CORRECT
func NewPipelineEngine(
    scheduler contracts.KernelScheduler,
    pluginHost contracts.PluginClient,
) *PipelineEngine {
    return &PipelineEngine{
        scheduler: scheduler,
        pluginHost: pluginHost,
    }
}

// INCORRECT (Forbidden)
func NewPipelineEngine() *PipelineEngine {
    return &PipelineEngine{
        scheduler: global.GetScheduler(), // Hidden dependency
    }
}
```

## 4. Service Composition (App Wiring)
The only place where the service graph is instantiated is at the very edge of the application: the `main()` function (or a dedicated `wire()` function called by `main()`).
This is the only layer that knows about concrete implementations.

```go
func main() {
    // 1. Core Infrastructure
    eventBus := eventbus.NewMemoryBus()
    memoryManager := memory.NewVFSManager(workspacePath)
    
    // 2. Kernel Boot
    scheduler := kernel.NewScheduler(memoryManager, eventBus)
    
    // 3. Inference Boot
    pluginHost := grpc.NewPluginHost()
    inferenceEngine := inference.NewEngine(pluginHost)
    
    // 4. Runtime Boot
    pipelineEngine := runtime.NewPipelineEngine(scheduler, inferenceEngine)
    workflowEngine := runtime.NewWorkflowEngine(pipelineEngine)
    
    // 5. Start Daemon
    daemon := server.NewDaemon(workflowEngine)
    daemon.Listen(":8080")
}
```

## 5. Testability & Mocks
Because every dependency is injected via a `pkg/contracts` interface, testing the `PipelineEngine` does not require booting a real `Kernel`.
Developers can inject trivial mocks (generated by tools in `/tools/mock-generator`) directly into the constructor.

```go
func TestPipelineEngine(t *testing.T) {
    mockScheduler := mocks.NewMockScheduler()
    mockPluginHost := mocks.NewMockPluginHost()
    
    engine := NewPipelineEngine(mockScheduler, mockPluginHost)
    
    // Test logic...
}
```

## 6. Conclusion
By strictly enforcing Constructor Injection and manual Service Composition, Fénix ensures that the transition from the architectural concepts of the 100-Series to the Go implementation of the 200-Series remains clean, decoupled, and endlessly maintainable. The service graph is built once, explicitly, and is immune to the unpredictability of magic DI frameworks.
