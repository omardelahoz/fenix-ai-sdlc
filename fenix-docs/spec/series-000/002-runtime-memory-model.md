# SPEC-002: Runtime Memory Model

## 1. Executive Summary
In a standard Operating System, the Memory Manager allocates RAM to prevent processes from starving each other or crashing the system.
Fénix processes hundreds of AI Tasks concurrently across vast software repositories. If every `Task` loaded the entire repository into memory, Fénix would instantly collapse via Out-Of-Memory (OOM) errors and exhaust API token limits.

The **Runtime Memory Model** defines how the **Memory Manager** of the Fénix Kernel handles hierarchical caches and isolates `ExecutionSnapshots` so that massive concurrency remains efficient and fast.

## 2. The Hierarchical Cache Architecture
Fénix uses a tiered memory system analogous to L1/L2/L3 CPU caches, extending all the way to external Provider networks.

### Level 1: Workspace Cache
The highest local level. Contains immutable organization standards, global profiles, and enterprise constraints. Loaded once per Fénix daemon boot.
*Size: Very Small. Lifespan: Daemon Uptime.*

### Level 2: Product Cache
Contains the `Product Definition` (Vision, Personas, Epics, Business Rules). Shared across all Projects within the Product.
*Size: Small. Lifespan: Product Session.*

### Level 3: Project Cache
The physical repository state. The `Artifact Store` (File System) indexes all files, AST representations, and the `Engineering Knowledge Graph` specific to the current repo (e.g., `booking-api`).
*Size: Large (Can be hundreds of MBs of code).*

### Level 0: Execution Snapshot (Registers)
The actual memory allocated to a specific `ExecutionPackage` (PCB). It contains **only** the strict subset of data (pointers/copies of AST nodes) required for one specific Task.
*Size: Strictly enforced by `Policies.MaxTokens`. Lifespan: Task Execution.*

### Level ∞: Provider Prompt Cache
The external cache maintained by LLM providers (e.g., Anthropic Prompt Caching, Gemini Context Caching). Fénix designs its L0 Serialization specifically to maximize L∞ cache hits, drastically reducing API costs and TTFT (Time To First Token).

## 3. The Lifecycle of an Execution Snapshot (Memory Manager)

The **Memory Manager** replaces the old "Context Manager" concept. Its pipeline is:
`Discover -> Dependency Resolver -> Snapshot Builder -> Snapshot Optimizer -> Snapshot Serializer`.

1. **Lazy Evaluation:** The Scheduler holds lightweight `ExecutionDescriptors`. Only when a Worker is available does the Memory Manager execute the pipeline to build the PCB.
2. **Discover & Resolve:** It queries the L3 `Project Cache` to resolve dependencies via the Knowledge Graph.
3. **Snapshot Build (CoW):** To save RAM, the `ExecutionSnapshot` does not duplicate the string contents of `AuthService.go`. It stores a reference pointer to the AST node in the L3 cache.
4. **Optimize:** It applies the `CompressionStrategy` policy.
5. **Serialize:** Only when the package is handed to the `Provider Adapter` (Device Driver) does the memory expand into a text string payload.

## 4. Advanced Hardware Alignment: NUMA and Worker Affinity
While Fénix can run on a laptop, its Kernel is designed for server-grade deployment. The Memory Model accounts for **NUMA (Non-Uniform Memory Access)** and **Worker Affinity**.
- **Local vs Shared Cache:** Workers executing Tasks from the same `Project` (e.g., `booking-api`) are pinned to the same logical CPU cores/nodes to share the L3 Project Cache natively in RAM without expensive cross-node memory copies.
- **Affinity Scheduling:** The Scheduler prefers assigning an `ExecutionDescriptor` to a Worker that already has the required L3 and L2 caches hot.

## 5. Cache Invalidation and EKG Triggers
Concurrency breeds race conditions. If `Task A` (Backend) modifies a struct in `Models.go`, and `Task B` (Frontend) is currently executing relying on the old `Models.go`:
1. `Task A` completes and the `Artifact Store` commits the change.
2. The `Knowledge Graph` detects a mutation in `Models.go`.
3. The `Memory Manager` invalidates the L3 cache for `Models.go`.
4. The Kernel checks if any active `ExecutionHandle` points to a PCB holding a snapshot dependent on `Models.go`.
5. If so, `Task B` is interrupted via its `CancellationToken`. Its Handle is faulted, and a new PCB (v2) is generated by the Memory Manager for a retry.

## 6. Conclusion
The Runtime Memory Model guarantees that Fénix can orchestrate a massive team of parallel AI Executors without exhausting system RAM or API rate limits. By mapping project files to a hierarchical cache and pushing caching all the way to L∞ (Cloud Providers), Fénix operates with the reliability and performance of an industrial-grade Operating System.
