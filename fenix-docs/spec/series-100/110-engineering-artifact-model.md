# SPEC-110: Engineering Artifact Model & Canonical Schema

## 1. Executive Summary
Before writing a single line of code for the Fénix Parser, Runtime, or Kernel, a single universal truth must be established: **The Fénix ABI (Artifact Binary Interface)**.

Throughout the SDLC, Fénix generates countless Intermediate Representations (IRs): `RequirementsIR`, `ArchitectureIR`, `CodeIR`, `TestIR`. If these objects lack a standardized metadata schema, caching, dependency resolution, and visualization become impossible.

This SPEC defines the **Canonical Schema** that every Engineering Artifact must conform to. It dictates mandatory metadata, deterministic hashing for cache invalidation, and relational linkages.

## 2. The Universal Artifact Schema
Every artifact generated by Fénix (either parsed from FDL or outputted by a Processor) must implement the following core schema when serialized (e.g., as JSON) in the VFS:

```json
{
  "id": "art_2a7b8c9d...",
  "type": "ArchitectureIR",
  "version": "v1.2.0",
  "schema_version": "1.0",
  
  "metadata": {
    "created_at": "2026-07-13T10:00:00Z",
    "created_by": "Processor: com.fenix.arch_designer@1.0",
    "status": "APPROVED",
    "hash": "sha256:d4e5f6..."
  },
  
  "relations": {
    "depends_on": ["art_1b2c3d4e..."],
    "implements": ["req_7x8y9z..."],
    "tests": []
  },
  
  "payload": {
    // Artifact-specific data (e.g., C4 Model, OpenAPI Spec, Go Code)
  }
}
```

## 3. Mandatory Metadata Explained
- **ID:** A globally unique identifier (e.g., KSUID or UUIDv7) that the Kernel VFS uses to store the artifact.
- **Type:** The explicit FDL profile this artifact adheres to (e.g., `ProductIR`, `SecurityIR`).
- **Version:** Semantic versioning of the artifact itself (e.g., the 3rd iteration of the architecture is `v3.0.0`).
- **Schema Version:** The version of the `payload` schema used (allows the parser to migrate old formats).
- **Status:** The orchestration state (e.g., `DRAFT`, `PENDING_REVIEW`, `APPROVED`, `DEPRECATED`).
- **Created By:** The exact Processor ID or Human ID that produced this artifact.

## 4. The Relational Graph
SDLC is a web of dependencies. An architecture document (`ArchitectureIR`) *implements* a product requirement (`RequirementsIR`). A test suite (`TestIR`) *tests* a code module (`CodeIR`).

The `relations` block enforces a directed acyclic graph (DAG) at the artifact level. The `SemanticQuery` service of the Runtime uses these relations to traverse the graph (e.g., "Find all CodeIRs that implement Requirement X").

## 5. Cache Invalidation & Deterministic Hashing
Fénix relies heavily on the Inference Cache to save LLM costs. To do this, it must know exactly when an artifact's content has changed.

The `hash` is a deterministic SHA-256 calculation.
**Hash Formula:**
`Hash = SHA256( Serialize(Payload) + Serialize(Relations.depends_on) )`

By including `depends_on` in the hash, Fénix implements cascading cache invalidation. If a `RequirementIR` changes, its hash changes. Consequently, the `ArchitectureIR` that depends on it will recalculate its hash, instantly invalidating any cached inference results further down the pipeline.

## 6. Serialization Format
While the in-memory representation is strongly typed Go structs, the persisted physical format in the Workspace's `_fenix/artifacts/` directory MUST be **Structured JSON**.

JSON is chosen over binary formats (like Protobuf) for artifacts because:
1. It is natively readable by humans for debugging.
2. It is trivially parsed by the LLMs during the Context Building phase.
3. It integrates seamlessly with standard diff tools (git).

## 7. Schema Evolution
When Fénix upgrades, the shape of a `RequirementsIR` might change. 
The system enforces **Forward Migrations**. If the Runtime encounters an artifact with `schema_version: 1.0` but the current Fénix daemon expects `2.0`, the specific Schema Plugin must provide a migration function:
`Migrate(Payload_v1) -> Payload_v2`
This guarantees backwards compatibility across long-running projects.

## 8. Conclusion
The Canonical Artifact Schema is the DNA of Fénix. By enforcing a strict ABI with graph relations and deterministic hashing, Fénix ensures that every piece of knowledge—whether written by a human or generated by an AI—is universally queryable, version-controlled, and instantly accessible to the Inference Engine.
